# 运行详情实时同步优化设计

## 目标

将运行详情页从“WebSocket 推送与固定 5 秒全量轮询同时工作”调整为“WebSocket 主推送、断线轮询兜底、日志增量补偿”，在不降低状态和日志实时性的前提下消除稳定连接期间的重复 HTTP 请求。

## 当前问题

- 页面挂载时请求一次运行详情和全量日志，WebSocket 建连后收到初始 `snapshot` 又会触发同样的两次请求。
- WebSocket 正常连接时仍固定每 5 秒请求运行详情和全量日志。
- 每个 `status` 或 `snapshot` 消息都会创建独立的延迟刷新，连续事件可能产生并发重复请求。
- 页面操作共用同时刷新详情和日志的 `load()`，即使只有运行结构变化，也会重复下载日志。
- WebSocket 断开后没有重连状态管理；固定轮询实际承担了隐式兜底职责，但连接正常时也一直产生开销。

## 方案

### 后端增量日志接口

保持 `GET /api/v1/runs/{run_id}/logs` 的响应结构和现有查询参数兼容，新增可选参数：

```http
GET /api/v1/runs/{run_id}/logs?after_id=1234
```

- 未提供 `after_id` 时保持现有行为，用于详情页首次加载。
- 提供 `after_id` 时仅返回 `id > after_id` 的日志。
- 返回结果按 `id` 升序排列并继续保留单次最多 5000 条的限制。
- 前端增量补偿收到 5000 条时继续使用最后一条日志 ID 拉取下一页，直到返回不足 5000 条。
- `after_id` 必须是非负整数；非法值由 FastAPI 返回参数校验错误。
- 不修改响应模型，不引入数据库迁移。

### 前端职责拆分

`useRunLifecycle` 内部拆分为两个独立同步操作：

- `loadRun()`：只请求运行详情；作为原有公开 `load` 的实现，供运行操作、节点操作和配置保存后的刷新继续使用。
- `loadLogs()`：首次加载当前日志集合。
- `syncLogsAfter(lastId)`：WebSocket 重连或断线轮询时增量补齐日志。

日志合并以 `id` 为唯一键，保持 ID 升序，避免初始 HTTP、增量 HTTP 和 WebSocket 事件交错时出现重复记录。

### WebSocket 主同步

页面挂载后并行执行一次初始详情和日志加载，并建立 WebSocket，避免在 HTTP 加载与事件订阅之间留下日志丢失窗口。初始 HTTP 日志也通过 ID 合并而非直接覆盖已经收到的 WebSocket 日志：

- `snapshot`：直接更新已有运行对象的 `status` 和 `progress`，不再触发 HTTP 请求。
- `status`：立即更新 `status` 和 `progress`，并通过 200ms 合并刷新仅请求一次运行详情，以同步步骤、产物、指标等完整结构。
- `log`：按日志 ID 去重后直接追加，不触发 HTTP 请求。
- WebSocket 保持连接期间不启动固定轮询。

详情刷新使用单飞机制：同一时刻只允许一个运行详情请求；请求过程中收到新的刷新信号时，在当前请求完成后至多再执行一次，避免丢失最新状态，也避免并发请求的旧响应覆盖新响应。

### 断线、重连与轮询兜底

非终态运行的 WebSocket 断开后：

1. 立即执行一次详情和增量日志校准。
2. 启动每 5 秒一次的兜底同步，只请求运行详情和最后日志 ID 之后的增量日志。
3. 按 `1s、2s、5s、10s、30s` 的退避序列尝试重连，后续保持 30 秒上限。
4. 重连成功后停止兜底轮询，并执行一次详情和增量日志校准，覆盖断线与重连交界处的竞态窗口。

同一时间只能存在一个 WebSocket、一个重连计时器和一个兜底轮询计时器。组件卸载时关闭连接并清理所有计时器及待执行的合并刷新。

### 终态处理

以下状态视为终态：`completed`、`cancelled`、`execution_failed`、`parse_failed`、`precheck_failed`、`timed_out`。

- 从 WebSocket 或 HTTP 发现终态后，停止兜底轮询和后续重连。
- 已连接的 WebSocket 保留到组件卸载，以接收可能紧随终态状态到达的最后日志；连接一旦断开便不再重连。
- 初始详情加载确认运行已经是终态时，关闭并行建立的 WebSocket，且不再重连。
- 用户触发报告重新生成等终态页面操作时，公开 `load()` 仍可手动刷新运行详情。

## 错误处理

- 单次详情或日志同步失败不清空当前页面数据。
- 断线期间的同步失败不会阻止后续轮询和重连。
- WebSocket 重连始终重新读取当前 `access_token`；HTTP 的现有拦截器可以刷新过期令牌，后续重连自然使用新令牌。
- 所有后台异步任务显式捕获异常，避免产生未处理的 Promise rejection。

## 兼容性与范围

- 保留原有日志接口的列表响应和过滤参数，已有调用方无需修改。
- `useRunLifecycle` 继续返回 `{ load, logs, run }`，运行详情页的其他 composable 无需更改调用接口。
- 不修改 WebSocket 服务端事件格式和内存事件代理。
- 不引入通用状态管理库、持久化事件流或数据库结构调整。

## 测试

### 后端

- 验证未提供 `after_id` 时保持原有日志列表行为。
- 验证 `after_id` 仅返回更大 ID 的日志并保持升序。
- 验证 `after_id` 与现有过滤条件可组合使用。

### 前端

- 首次挂载只请求一次详情和一次日志，初始 `snapshot` 不产生额外 HTTP 请求。
- WebSocket 正常连接时推进定时器不会触发固定轮询。
- 连续 `status` 消息只产生一次合并后的详情请求，不请求日志。
- `log` 消息直接追加并按 ID 去重。
- WebSocket 断开后立即校准并启动兜底轮询与退避重连。
- 重连成功后停止轮询，并使用最后日志 ID 增量补偿。
- 终态停止轮询和重连，但已连接 WebSocket 仍可接收最后日志。
- 组件卸载会清理连接和全部计时器。

最终运行相关后端测试、前端测试和前端生产构建。
